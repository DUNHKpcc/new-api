# 邀请奖励与代理充值佣金设计规范

状态：设计定稿，待实现
版本：V1
日期：2026-08-09

## 1. 目标

在保留现有注册邀请奖励的基础上，新增独立的代理充值佣金业务：

- 所有用户都可以使用邀请链接并查看邀请成果。
- 注册邀请奖励由管理员独立开启和配置。
- 达到资格并主动开启代理的用户，可以从其邀请用户的真实充值中获得比例佣金。
- 注册邀请奖励与代理充值佣金可以分别开启，也可以同时生效。
- 代理资格、充值金额、佣金计算和佣金转移均由后端判定，前端不参与可信计算。

## 2. V1 范围

### 2.1 包含

- 侧边栏“个人”分组新增“代理中心”。
- 钱包中的邀请链接、邀请人数和邀请奖励迁移到代理中心。
- 保留现有固定注册邀请奖励。
- 新增基于真实充值金额的一级代理佣金。
- 新增代理资格门槛、用户级资格覆盖和代理状态。
- 新增佣金账本、待结算、可转入、转入余额及冲正能力。
- V1 仅统计和结算 Epay 在线充值。

### 2.2 不包含

- 多级代理或团队层级。
- 现金提现、银行卡提现或外部打款。
- 按 API 消费金额分佣。
- Stripe、Creem、Waffo 等其他支付渠道的佣金。
- 排行榜、推广海报、二维码和营销素材中心。

## 3. 核心概念

### 3.1 注册邀请奖励

用户 B 使用用户 A 的邀请链接注册成功后，按照管理员配置发放固定额度：

- A 获得邀请人固定奖励。
- B 获得被邀请人固定奖励。
- 是否发放由“注册邀请奖励”开关控制。
- 该奖励不要求 B 充值，也不要求 A 已经开启代理。

### 3.2 代理充值佣金

用户 B 与 A 建立邀请关系后，B 的符合条件的真实充值可以为 A 产生比例佣金：

```text
真实充值价值 x 充值佣金比例 = A 的佣金价值
```

例如：

```text
B 真实支付 $50
管理员设置充值佣金比例为 50%
A 获得 $25 等值系统额度
```

只有 A 在该笔充值完成时处于有效代理状态，才生成充值佣金。

### 3.3 两种奖励相互独立

| 注册邀请奖励 | 代理充值佣金 | 结果 |
| --- | --- | --- |
| 关闭 | 关闭 | 仅建立邀请关系，不发奖励 |
| 开启 | 关闭 | 注册时发放固定邀请奖励 |
| 关闭 | 开启 | 注册不发奖励，真实充值时发放代理佣金 |
| 开启 | 开启 | 注册奖励和真实充值佣金分别发放 |

两种奖励必须使用不同的账目和页面指标，不得混合成一笔“总奖励”。

## 4. 邀请关系

- V1 复用现有 `aff_code` 作为邀请代码。
- V1 复用现有 `inviter_id` 保存 B 的直接邀请人 A。
- 邀请关系在注册完成后不可由普通用户修改。
- A 不需要开启代理，也可以分享邀请链接并获得已启用的注册邀请奖励。
- B 注册时 A 必须是有效、可用的用户，禁止自邀。
- 邀请人数按成功建立邀请关系的用户数统计，与注册奖励金额是否为零无关。
- A 后续开启代理后，B 在此后发生的新充值可以产生佣金；开启代理前的历史充值不追溯补发。

## 5. 代理资格

### 5.1 全局配置

管理员可以配置：

- 是否开启代理充值佣金。
- 开启代理所需的已核验充值总额。
- 资格币种，V1 与 Epay 结算币种保持一致，不跨币种累计。
- 全局充值佣金比例。
- 佣金等待期，默认 7 天，允许配置为 0 天。

门槛金额使用最小货币单位存储。例如 `$100.00` 保存为 `10000` 美分。

### 5.2 用户级权限

用户管理界面提供三态配置：

- `inherit`：遵循系统充值门槛，默认值。
- `allow`：管理员允许用户跳过充值门槛。
- `deny`：禁止用户开启或继续使用代理充值佣金。

资格计算：

```text
代理充值佣金全局开启
且用户权限不是 deny
且以下条件之一成立：
  - 用户权限为 allow
  - 用户权限为 inherit，且已核验充值总额达到门槛
```

### 5.3 代理状态

- `inactive`：尚未开启代理。
- `active`：代理正常，可从后续真实充值获得佣金。
- `suspended`：代理佣金权限被管理员暂停。

达到门槛只代表可以开启，用户仍需主动点击“开启代理”。管理员设置 `allow` 也不自动激活。

调整全局门槛只影响尚未开启的用户，不自动取消已经开启的代理。管理员将用户权限设置为 `deny` 时，已开启代理变为 `suspended`。

暂停只影响充值佣金。该用户的邀请链接、邀请人数、历史注册邀请奖励仍然保留；如果注册邀请奖励全局开启，仍按独立规则处理注册邀请奖励。

## 6. 已核验充值口径

V1 仅将满足以下全部条件的 Epay 充值计入资格和佣金：

- 支付回调签名验证成功。
- 回调状态明确为支付成功。
- 内部订单存在且支付渠道为 Epay。
- 回调实付金额可解析且大于零。
- 回调实付金额与内部订单应付金额完全一致。
- Epay 平台交易号存在。
- 订单由支付回调完成，不是管理员人工补单。
- 订单尚未被退款、撤销或冲正。

明确排除：

- 注册赠送额度。
- 注册邀请奖励和代理佣金转入。
- 兑换码、套餐额度和管理员额度调整。
- 管理员人工完成的充值订单。
- 金额异常、缺少平台流水号或缺少支付凭据的订单。
- V1 范围外的支付渠道。

历史订单如果缺少实付金额、币种或平台交易号，不自动计入。后续如需补录，必须通过独立的管理员核验和审计流程完成。

## 7. 佣金计算

### 7.1 比例

佣金比例使用基点存储：

```text
1% = 100 bps
50% = 5000 bps
100% = 10000 bps
```

比例范围为 `0` 至 `10000`。每笔佣金保存支付完成时的比例快照；管理员修改比例只影响之后完成的充值。

### 7.2 计算基数

佣金必须基于 B 的真实实付金额，不能基于：

- B 获得的最终额度。
- 充值赠送额度。
- 用户分组优惠后的目标额度。
- 当前管理员配置推算出的金额。

订单创建时必须保存结算币种和单位价格快照。支付完成后先根据实际支付金额和订单价格快照换算真实充值价值，再计算佣金。不得读取可能已经改变的当前价格配置。

```text
commission_value_minor = floor(paid_amount_minor x rate_bps / 10000)
reward_quota = commission_value 按订单价格快照换算为系统额度
```

额度换算必须使用项目统一的安全额度转换函数，禁止裸 `float64 -> int` 转换，禁止产生负数额度。

### 7.3 示例

USD 结算：

```text
实付金额：$50.00
佣金比例：50%
佣金价值：$25.00
```

非 USD 结算：

```text
订单价格快照：¥7.20 / $1 额度
实付金额：¥360.00
佣金比例：50%
佣金价值：¥180.00
最终奖励：$25.00 等值系统额度
```

## 8. 佣金生成条件

每笔佣金必须同时满足：

- B 存在有效 `inviter_id`，对应邀请人 A。
- A 与 B 不是同一个用户。
- A 在支付完成时处于 `active`。
- 代理充值佣金全局开启。
- 充值满足“已核验充值口径”。
- 充值完成时间不早于 A 的代理开启时间。
- 同一个充值订单尚未生成佣金。

V1 对 B 的每一笔符合条件的真实充值生成佣金，不限首次充值。

必须以充值订单 ID 建立唯一约束，保证重复回调、并发回调和服务重试不会重复发放佣金。

## 9. 佣金生命周期

```text
支付成功 -> pending -> available -> transferred
                         \
                          -> reversed
```

- `pending`：等待期内，不可转入余额。
- `available`：等待期结束，可以转入主余额。
- `transferred`：已经转入主余额。
- `reversed`：充值退款或管理员冲正，佣金作废。

等待期为 0 天时，可以在支付完成后直接进入 `available`。

### 9.1 转入余额

- 注册邀请奖励与充值佣金分别转入，不共用一条流水。
- 转入操作必须使用事务和行锁。
- 同一笔可用佣金最多转入一次。
- 转入成功后增加 A 的主额度，并记录转入流水。
- 支付合规未确认时，不允许转入。

### 9.2 退款和冲正

- 未转入的佣金直接标记为 `reversed`。
- 已转入的佣金不得直接把用户主额度扣成负数。
- 已转入部分形成佣金欠额，后续新佣金优先抵扣。
- V1 如果 Epay 无自动退款通知，由管理员从具体充值订单执行佣金冲正。
- 所有冲正必须保存操作者、原因、时间和关联充值订单。

## 10. 数据设计

### 10.1 用户代理字段

建议在用户代理资料中保存：

```text
affiliate_access            inherit | allow | deny
affiliate_status            inactive | active | suspended
affiliate_activated_at      开启时间
affiliate_qualified_amount  开启时已核验充值金额快照
affiliate_currency          资格币种
```

不能用 `aff_code` 是否为空判断代理是否开启，因为现有用户可能已经拥有邀请码。

### 10.2 佣金流水

每笔佣金至少保存：

```text
id
agent_user_id
referred_user_id
topup_id                    唯一
provider_trade_no
paid_amount_minor
paid_currency
unit_price_snapshot
commission_rate_bps
commission_amount_minor
reward_quota
status
available_at
transferred_at
reversed_at
reverse_reason
created_at
```

佣金流水是审计事实，不允许覆盖历史金额、比例和价格快照。

### 10.3 邀请关系与注册奖励流水

现有 `users.inviter_id` 可以继续作为快速查询字段，但不足以独立证明邀请绑定和固定奖励是否已经执行。V1 应增加不可变的邀请关系与注册奖励记录：

```text
affiliate_referrals
  id
  inviter_user_id
  referred_user_id            唯一
  aff_code_snapshot
  bound_at

affiliate_signup_rewards
  id
  referral_id
  beneficiary_user_id
  beneficiary_role            inviter | invitee
  reward_quota
  status                      granted | reversed
  config_version
  created_at
```

- `referred_user_id` 唯一，保证同一新用户只绑定一个邀请人。
- `(referral_id, beneficiary_role)` 唯一，保证注册重试不会重复发放 A 或 B 的固定奖励。
- 邀请人数以邀请关系记录为准，不再依赖 `aff_count` 是否因奖励大于零而增加。
- 注册邀请奖励记录和充值佣金记录必须分表或通过明确的业务类型隔离，不能只依赖文本日志区分。

## 11. API 设计

### 11.1 用户接口

```http
GET  /api/user/affiliate/overview
POST /api/user/affiliate/activate
GET  /api/user/affiliate/commissions
POST /api/user/affiliate/invite-rewards/transfer
POST /api/user/affiliate/commissions/transfer
```

`overview` 返回：

- 邀请链接和邀请码。
- 邀请人数。
- 注册邀请奖励的可转金额和累计金额。
- 代理状态、权限来源和是否满足资格。
- 已核验充值总额、门槛及还差金额。
- 当前佣金比例和等待期。
- 待结算、可用、已转入及累计佣金。

所有金额使用最小货币单位并以字符串返回，避免 JavaScript 大整数和浮点精度问题。

### 11.2 管理员接口

```http
PUT  /api/user/:id/affiliate-access
GET  /api/admin/affiliate/commissions
POST /api/admin/affiliate/commissions/:id/reverse
```

管理员不能直接输入并覆盖用户累计佣金。异常处理必须关联具体佣金或充值订单。

## 12. 前端设计

### 12.1 侧边栏和路由

“个人”分组顺序：

```text
钱包
代理中心
个人设置
```

- 路由：`/affiliate`
- 图标：`Handshake`
- 入口不根据用户是否开启代理而隐藏。
- 入口仍受管理员侧边栏模块配置控制，建议配置键为 `personal.affiliate`。
- 注册邀请奖励和代理充值佣金均全局关闭时，可以隐藏入口。

### 12.2 钱包迁移

从钱包页移除现有邀请奖励卡，将以下能力完整迁入代理中心：

- 邀请链接。
- 复制邀请链接。
- 邀请人数。
- 可转注册邀请奖励。
- 累计注册邀请奖励。
- 注册邀请奖励转入余额。

钱包页继续负责充值、余额、订阅和资金记录，不再重复展示邀请信息。

### 12.3 代理中心结构

```text
代理中心
├── 邀请推广
├── 注册邀请奖励
├── 代理资格与状态
├── 充值佣金概览
└── 充值佣金明细
```

#### 邀请推广

对所有用户显示：

- 邀请链接和复制按钮。
- 邀请人数。
- 当前注册邀请规则。

未开启代理的用户仍可邀请并查看邀请人数及注册邀请奖励。

#### 注册邀请奖励

独立显示：

- 可转注册邀请奖励。
- 累计注册邀请奖励。
- 邀请人固定奖励规则。
- 被邀请人固定奖励规则。
- 转入余额按钮。

#### 代理资格与状态

未达标时显示：

```text
已核验充值总额
代理开启门槛
还差金额
充值进度
前往充值
```

达到门槛或管理员允许时显示“开启代理”。管理员禁止时显示不可开启状态，不影响基础邀请功能。

#### 充值佣金

只有已经开启代理的用户显示完整佣金数据：

- 当前佣金比例。
- 被邀请用户累计已核验充值。
- 待结算佣金。
- 可用佣金。
- 累计佣金。
- 佣金转入余额按钮。

未开启代理时显示功能说明和当前资格进度，不显示虚构佣金数据。

#### 佣金明细

桌面端使用表格，移动端使用纵向列表：

| 时间 | 被邀请用户 | 真实充值 | 比例 | 我的佣金 | 状态 |
| --- | --- | ---: | ---: | ---: | --- |
| 08-09 14:30 | us***23 | $50.00 | 50% | $25.00 | 待结算 |

被邀请用户信息必须脱敏，不展示完整邮箱、手机号或用户名。

### 12.4 用户管理

用户列表新增“代理状态”列：

- 普通用户。
- 可开启。
- 已开启。
- 已暂停。
- 禁止成为代理。

用户行操作新增“代理设置”：

- 遵循系统门槛。
- 允许成为代理。
- 禁止成为代理。
- 查看已核验充值总额。
- 查看开启时间和累计佣金。

用户管理界面不得提供直接修改累计佣金的输入框。

### 12.5 管理员设置

在计费设置中分成两个独立区块。

注册邀请奖励：

- 开启注册邀请奖励。
- 邀请人固定奖励。
- 被邀请人固定奖励。

代理充值佣金：

- 开启代理充值佣金。
- 开启代理所需的充值总额。
- 充值佣金比例。
- 佣金等待期。
- 当前覆盖支付渠道，V1 显示“在线支付”。
- 计算预览，例如“用户充值 $50，代理获得 $25”。

用户端不显示 Epay 名称，统一显示“已核验充值总额”和“在线支付”。

## 13. 安全与一致性要求

- 前端展示的充值总额不得作为激活或佣金依据。
- `activate` 必须在后端重新计算资格并保证幂等。
- 支付完成、用户充值额度、佣金流水创建应处于一致的事务边界。
- 订单锁必须使用项目跨数据库的 `lockForUpdate`。
- 佣金订单使用唯一约束保证幂等，不能只依赖进程内锁。
- 金额和比例使用整数或 Decimal 计算，不使用二进制浮点进行财务结算。
- 所有数据库逻辑必须兼容 SQLite、MySQL 和 PostgreSQL。
- 佣金创建失败不得静默吞掉，必须记录可关联充值订单的告警并支持安全重试。
- 普通用户不能查看其他用户的完整身份、充值订单或佣金明细。

### 13.1 当前日志现状

当前代码已经有部分文本日志，但没有覆盖完整业务事实：

- B 获得被邀请人固定奖励时，会给 B 写入 `LogTypeSystem` 日志，内容类似“使用邀请码赠送”。
- A 获得邀请人固定奖励时，会给 A 写入 `LogTypeSystem` 日志，内容类似“邀请用户赠送”。
- 邀请关系绑定成功本身没有独立、结构化日志。
- 当邀请人固定奖励为零时，当前不仅不写奖励日志，也不会正确增加 `aff_count`。
- 注册邀请奖励转入主余额当前没有独立业务日志。
- B 的 Epay 充值成功会给 B 写入 `LogTypeTopup` 日志，但不会给 A 写“被邀请用户充值”记录。
- 当前尚未实现充值佣金，因此没有佣金生成、结算、转入或冲正日志。
- `RecordLog` 和 `RecordTopupLog` 写入失败时只写系统错误，不会回滚资金操作；文本日志不能作为资金事实来源。

### 13.2 V1 日志分层

V1 必须同时保留四层记录，不得只写一条中文文本：

1. **业务账本**：邀请关系、固定注册奖励、充值订单和佣金流水，是最终事实来源。
2. **用户可见日志**：让 A、B 在自己的记录中看到邀请奖励、充值佣金和转入结果。
3. **管理员审计日志**：记录资格覆盖、暂停、恢复、配置变更和佣金冲正。
4. **服务运行日志**：记录回调验签失败、事务失败、唯一约束冲突和日志投递失败，用于告警排障。

业务账本必须先于文本日志存在。即使日志数据库暂时不可用，也不能丢失邀请或佣金事实；恢复后应能从主库业务账本补发用户日志和审计日志。

### 13.3 必须记录的业务事件

| 事件 | 记录归属 | 用户可见 | 必要字段 |
| --- | --- | --- | --- |
| `affiliate.referral_bound` | A、B 的邀请关系账本 | A 可见邀请人数变化，B 可见邀请来源可选 | `referral_id`、A、B、绑定时间、邀请码快照 |
| `affiliate.signup_reward_granted` | A 或 B | 是 | `referral_id`、受益角色、奖励额度、配置版本 |
| `affiliate.signup_reward_transferred` | A | 是 | 转移额度、转移前后可用奖励、事务 ID |
| `affiliate.activated` | A | 是 | 资格来源、门槛、已核验金额、开启时间 |
| `affiliate.access_changed` | 管理员审计 | 否 | 目标用户、修改前后权限、操作者、原因 |
| `affiliate.commission_created` | A 的佣金账本 | 是 | `topup_id`、脱敏 B、实付金额、币种、比例、奖励额度、状态 |
| `affiliate.commission_available` | A | 是 | 佣金 ID、可用时间、可用额度 |
| `affiliate.commission_transferred` | A | 是 | 佣金 ID 或批次、转入额度、事务 ID |

### 13.4 日志字段与隐私

- 业务事件使用稳定的英文 `action`，展示文案通过前端 i18n 渲染。
- 金额保存为最小货币单位字符串，比例保存为 bps，额度保存为整数。
- 用户日志中的 B 必须脱敏；完整用户 ID、平台流水号和回调调试字段仅管理员可见。
- 不记录 Epay 密钥、签名原文、完整回调参数、Cookie、访问令牌或完整邮箱/手机号。
- 所有事件包含稳定事件 ID、关联订单/佣金 ID、创建时间和请求 ID，便于串联排查。
- 管理员配置、资格覆盖和冲正必须使用 `recordManageAudit` 同类结构化审计能力，并记录修改前后值，但不得记录密钥。
- 如果 `LOG_DB` 与主数据库分离，不能假设跨库事务。推荐在主库写入事务性 outbox，再异步、幂等地投递用户日志和管理员审计日志。

## 14. 最高风险后端链路与接口

本节基于 2026-08-09 当前工作区代码。实现期间如果接口或函数迁移，必须同步更新本节。

### 14.1 风险等级

- `P0`：可能造成未收款发额度、重复发额度、重复佣金、资金账不平或无法追偿。
- `P1`：可能造成资格绕过、奖励漏发、配置误用、历史数据错误或越权操作。

### 14.3 当前支付回调存在的 P0 问题

当前 `controller.EpayNotify` 不能直接作为佣金触发点，存在以下阻断问题：

1. 回调金额解析失败、金额为零或金额不一致时只记录警告，仍可能将订单改为成功并增加额度。
2. 验签成功后，在订单和用户额度持久化之前就向支付平台写出 `success`。后续数据库失败时，支付平台可能不再重试。
3. 订单状态更新和用户额度增加不在同一个数据库事务中。可能出现“订单成功但用户未到账”，并且重试因订单已成功而跳过。
4. `LockOrder` 是单进程内存锁，多实例部署时不能阻止两个实例同时处理同一回调。
5. 当前先读取订单再保存状态，没有数据库行锁和基于 `pending` 状态的原子条件更新，多实例下存在重复到账风险。
6. `provider_trade_no` 当前只有普通索引，没有支付渠道与平台流水号组成的唯一约束，不能在数据库层阻止同一平台交易被重复关联。
7. 佣金如果作为订单成功后的额外写入，会进一步扩大“用户已到账但佣金漏发”或“佣金已生成但订单处理失败”的不一致窗口。

支付回调需要收敛为一个数据库事务中的结算服务：

```text
数据库锁定 pending 订单
-> 校验支付凭据与金额
-> 标记订单成功
-> 增加 B 的充值额度
-> 按条件创建唯一佣金流水
-> 提交事务
-> 更新/失效缓存
-> 最后向支付平台返回 success
```

事务失败必须返回 `fail`，允许支付平台安全重试。重试时以订单状态、平台流水号唯一约束和佣金 `topup_id` 唯一约束共同保证幂等。

### 14.4 注册邀请链路风险

当前注册奖励在用户创建事务提交后执行，并且部分额度更新错误被忽略：

- `model.User.finishInsert` 和 `FinalizeOAuthUserCreation` 调用奖励更新时使用 `_ = ...`，奖励失败不会让注册失败，也缺少可靠重试状态。
- `inviteUser` 使用读取用户后整体保存的方式增加 `aff_count`、`aff_quota` 和 `aff_history_quota`，没有行锁；并发注册可能发生丢失更新。
- 当前只有邀请人固定奖励大于零时才增加 `aff_count`，不符合“邀请人数独立于奖励金额”的新口径。
- `GetUserIdByAffCode` 当前只查询用户 ID，没有明确校验邀请人是否有效可用。

V1 实现必须把“邀请关系建立”和“固定注册奖励发放”拆成可审计、可幂等的事实。不能依靠重新执行整个注册流程补偿奖励。

### 14.5 配置和管理员权限风险

- 佣金比例直接决定平台支出，必须限制在 `0` 至 `10000 bps`，不得接受 NaN、无穷或负数。
- 门槛、比例、等待期和开关是同一业务配置。逐个调用通用 Option 接口可能产生短暂的半配置状态，推荐使用专用原子保存接口或带版本的整组配置。
- 开启非零注册奖励或充值佣金必须要求支付合规已经确认。
- “允许成为代理”可以绕过充值门槛，属于财务权限。建议仅 Root 用户可操作，即使入口放在用户管理页面。
- 佣金冲正必须是 Root 权限，不能复用普通用户额度调整接口。
- 配置变更只影响新充值，佣金流水必须保存配置版本、比例和价格快照。

## 15. 当前充值总额改动的风险面

当前工作区已经存在尚未提交的“已核验充值总额”相关改动。代理功能实现前必须先单独审查和收敛这些改动。

### 15.1 涉及文件和影响

| 文件 | 当前变化 | 风险 |
| --- | --- | --- |
| `controller/topup.go` | 解析 Epay 实付金额、记录平台流水号、增加汇总接口 | 位于真实支付回调主链路；当前金额异常仍放行，且回调事务问题未解决 |
| `model/topup.go` | `TopUp` 增加实付金额、币种和平台流水号；增加汇总查询 | 触发数据库迁移；历史数据为空；平台流水号未唯一；汇总成为后续资格基础 |
| `router/api-router.go` | 增加 `/api/user/topup/summary` | API 契约和缓存行为发生变化；必须保持仅本人可读 |
| `setting/operation_setting/payment_setting.go` | 增加 Epay 结算币种配置 | 管理员在下单与回调之间修改币种时，当前实现可能给订单写入错误币种 |
| `controller/option.go` | 校验并保存 Epay 币种 | 币种变更会影响后续统计分组，必须明确生效时间和禁止对历史数据重新解释 |
| `model/main.go` | 通过既有 AutoMigrate 间接迁移 `TopUp` 新字段 | 大表迁移可能锁表或延长启动时间，需要在三种数据库上验证并准备回滚 |
| `web/src/features/wallet/*` | 展示已核验充值总额 | 展示口径可能被误当成业务资格；前端不得自行判断代理激活 |

### 15.2 当前改动的具体风险

1. **金额异常仍会到账**：新增实付字段目前只是记录证据，没有把证据校验变成订单成功的前置条件。
2. **历史用户默认少算**：旧成功订单没有 `paid_amount_minor`、`paid_currency` 和 `provider_trade_no`，会被汇总查询排除。
3. **币种记录时点错误**：当前在回调时读取管理员的 Epay 当前币种，而不是使用订单创建时的币种快照。下单后修改配置会污染订单证据。
4. **平台流水号可重复**：缺少 `(payment_provider, provider_trade_no)` 唯一约束，数据库不能阻止重复平台交易证据。
5. **价格无法复现**：订单没有保存单位价格、用户分组倍率和金额折扣快照，未来无法稳定地把真实支付金额换算为佣金额度。
6. **汇总不含退款调整**：当前汇总只累加成功订单，没有退款或冲正负向记录，严格来说是“已核验累计实付”，不是可撤销后的净入账。
7. **币种切换会拆分累计值**：同一用户可能得到 CNY、USD 等多组总额。代理门槛不得把不同币种直接相加。
8. **迁移风险**：为生产 `top_ups` 表增加字段和索引需要验证 SQLite、MySQL、PostgreSQL 的启动迁移时间、锁影响和回滚方式。
9. **API 复用风险**：`/topup/summary` 是展示和通用查询接口，不应承担激活代理的授权职责；否则前端缓存、旧响应或伪造请求可能影响资格。
10. **现有订单处理非原子**：即使汇总字段正确，订单状态和用户额度仍可能因分步写入发生不一致，继而污染资格和佣金判断。

### 15.3 当前改动进入代理开发前的验收门槛

- 金额、币种和平台流水号必须在订单成功前完成严格校验。
- 订单创建时保存币种与单位价格快照。
- 回调结算改为数据库事务并使用 `lockForUpdate`。
- 平台流水号和佣金订单建立数据库唯一约束。
- 支付平台 `success` 响应只能在事务成功后返回。
- 明确历史订单策略，不把缺少证据的订单自动当作真实入账。
- 明确退款/冲正数据模型和汇总口径。
- 对 SQLite、MySQL、PostgreSQL 分别运行迁移与并发回调测试。
- 前端汇总接口与后端资格服务分别测试，证明前端数据不能影响激活结果。

## 16. 风险矩阵与控制措施

| 风险场景 | 可能后果 | 防护措施 | 必测回归 |
| --- | --- | --- | --- |
| 伪造或异常金额回调 | 少收款、多发额度和佣金 | 验签、金额精确匹配、平台流水唯一、失败关闭 | 0、负数、超精度、非数字、金额不一致 |
| 重复或并发回调 | B 重复到账、A 重复佣金 | 数据库锁、条件更新、唯一约束、幂等结算 | 同进程、跨连接、模拟多实例并发 |
| 数据库在结算中途失败 | 订单、额度、佣金三者不一致 | 单事务、提交后响应、可安全重试 | 每个写入点故障注入 |
| 管理员修改价格或比例 | 历史佣金被重新解释 | 订单和佣金快照、配置版本 | 下单后改价格、支付后改比例 |
| 币种切换 | 门槛误判、佣金换算错误 | 订单币种快照、禁止跨币种直接累计 | CNY/USD 分组和配置切换 |
| 注册并发 | 邀请人数或固定奖励丢失 | 原子增量、邀请奖励唯一流水 | 同一邀请人并发注册 |
| 转入与冲正并发 | 重复转入或无法追偿 | 行锁、状态机条件更新、欠额账本 | transfer/reverse 竞争 |
| 退款发生在转入之后 | 平台承担无法收回的佣金 | 等待期、欠额抵扣、管理员暂停 | pending/available/transferred 分别冲正 |
| 管理员误设 100% 佣金 | 利润被快速耗尽 | 范围校验、醒目预览、RootAuth、审计 | 边界值和配置回滚 |
| 多账号刷注册奖励 | 固定邀请奖励损失 | 风控、注册验证、频率限制、异常邀请审计 | 同设备/身份批量注册策略验证 |
| 普通管理员越权 | 绕过门槛、冲正或放大支出 | RootAuth 或专用权限、审计 | 角色权限矩阵 |
| 缓存与数据库不一致 | 页面余额错误或重复操作 | 事务后失效缓存、数据库为最终依据 | 转入后立即查询、缓存失败 |
| 日志数据库写入失败 | 资金成功但用户/管理员无记录 | 主库账本为准、事务性 outbox、幂等补发 | LOG_DB 不可用后恢复并补发 |

### 16.1 残余业务风险

以下风险不能只靠代码完全消除，运营上必须接受或补充策略：

- 支付成功后发生线下退款，但 Epay 没有可靠退款通知。
- A 与 B 是不同账号但由同一实际控制人操作，形成自买返佣。
- 50% 等高比例佣金超过真实毛利。
- 历史邀请关系在 A 开启代理后开始为未来充值产生佣金，可能增加原本未预期的支出。
- 等待期结束并转入主额度后，用户可能已经消费，退款只能通过未来佣金欠额追偿。

上线时必须保留全局关闭代理充值佣金的紧急开关。关闭后停止生成新佣金，但不得删除历史流水或改变已经生成的佣金状态。

## 17. 上线前置条件

Epay 回调当前必须先改为失败关闭：

```text
金额解析失败
金额小于等于零
平台交易号缺失
回调金额与订单金额不一致
=> 不完成订单、不增加额度、不计入充值总额、不生成佣金
```

在该前置条件完成前，不得上线代理资格或充值佣金。

## 18. 历史数据策略

- 已发放的注册邀请奖励不追回。
- 已有邀请关系继续保留。
- A 开启代理后，已有被邀请用户之后的新充值可以产生佣金。
- 代理开启前的充值不追溯补发佣金。
- 缺少支付凭据的历史充值不计入代理资格。
- 已有邀请码不代表已经开启代理。

## 19. 验收标准

### 19.1 注册邀请奖励

- 开关关闭时，注册只建立关系，不发固定奖励。
- 开关开启时，A、B 按配置分别获得固定奖励。
- 奖励金额为零时，邀请人数仍然正确增加。
- 注册重试不能重复发放奖励。

### 19.2 代理资格

- 低于门槛的 `inherit` 用户无法开启。
- 正好达到门槛时可以开启。
- `allow` 用户可以跳过门槛。
- `deny` 用户无法开启，已开启用户变为暂停。
- 前端伪造充值总额无法绕过后端检查。

### 19.3 充值佣金

- 只有真实核验充值产生佣金。
- A 未开启或已暂停时不产生佣金。
- 同一充值重复回调只生成一笔佣金。
- 佣金使用支付时比例和价格快照。
- 修改全局比例不改变历史佣金。
- 管理员补单不产生佣金。
- 退款或冲正可以关联原充值和原佣金。

### 19.4 前端

- 未开启代理的用户可以看到邀请链接、邀请人数和注册邀请奖励。
- 钱包页不再重复出现邀请推广卡。
- 注册邀请奖励与充值佣金视觉和文案明确分离。
- 长金额、长链接和移动端布局无溢出或遮挡。
- 加载、空数据、失败、禁止、暂停和待结算状态完整。
- 所有新增用户可见文本完成多语言同步。

### 19.5 日志与审计

- 邀请绑定、A/B 固定奖励、佣金生成、可用、转入和冲正均有可关联业务记录。
- 用户只能看到自己的奖励和脱敏后的关联用户信息。
- 管理员资格覆盖、配置变更和佣金冲正均有结构化审计日志。
- LOG_DB 暂时不可用时资金事务仍以主库账本为准，恢复后可以幂等补发日志。
- 重复请求或日志重投不会生成重复业务账目或重复用户日志。

## 20. 推荐实施顺序

1. 将 Epay 金额异常处理改为失败关闭，并完成回归测试。
2. 完成已核验充值证据字段和通用汇总接口。
3. 增加代理资格、状态和管理员配置。
4. 增加邀请关系账本、注册奖励账本、佣金账本和事务性日志 outbox。
5. 增加佣金幂等生成、等待期、转入和冲正。
6. 增加代理中心路由并迁移钱包邀请卡。
7. 增加用户管理代理权限和管理员配置界面。
8. 完成跨数据库、并发回调、日志补发、退款冲正和前端响应式验证。
