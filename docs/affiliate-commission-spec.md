# 邀请奖励与代理充值佣金设计规范

状态：V1 实现与回归验证中
版本：V1
日期：2026-08-11

## 1. 目标

在保留现有注册邀请奖励的基础上，新增独立的代理充值佣金业务：

- 所有用户都可以使用邀请链接并查看邀请成果。
- 注册邀请奖励由管理员独立开启和配置。
- 达到资格并主动开启代理的用户，可以从其邀请用户的真实充值中获得比例佣金。
- 注册邀请奖励与代理充值佣金可以分别开启，也可以同时生效。
- 代理资格、充值金额、佣金计算和佣金转移均由后端判定，前端不参与可信计算。

## 2. V1 范围

### 2.1 包含

- 侧边栏“个人”分组新增“代理中心”。
- 钱包中的邀请链接、邀请人数和邀请奖励迁移到代理中心。
- 保留现有固定注册邀请奖励。
- 新增一级代理佣金：转入余额按订单实际购买额度计算，未来现金提现按真实支付金额计算。
- 新增代理资格门槛、用户级资格覆盖和代理状态。
- 新增佣金账本、待结算、可转入、转入余额及冲正能力。
- V1 仅统计和结算 Epay 在线充值。

### 2.2 不包含

- 多级代理或团队层级。
- 真实支付宝打款、银行卡提现或其他外部出款；V1 只保存现金提现计价结果并在前端标记“未来支持”。
- 按 API 消费金额分佣。
- Stripe、Creem、Waffo 等其他支付渠道的佣金。
- 渠道侧真实退款、B 充值额度回收和支付净额账本。
- 排行榜、推广海报、二维码和营销素材中心。

## 3. 核心概念

### 3.1 注册邀请奖励

用户 B 使用用户 A 的邀请链接注册成功后，按照管理员配置发放固定额度：

- A 获得邀请人固定奖励。
- B 获得被邀请人固定奖励。
- 是否发放由“注册邀请奖励”开关控制。
- 该奖励不要求 B 充值，也不要求 A 已经开启代理。

### 3.2 代理充值佣金

用户 B 与 A 建立邀请关系后，B 的符合条件的真实充值可以为 A 产生比例佣金：

```text
转入余额奖励 = B 本次实际到账的购买额度 x 佣金比例
未来现金提现计价 = B 本次已核验的实付金额 x 佣金比例
```

例如：

```text
B 购买 $25 额度，实际支付 CNY 8.00
管理员设置充值佣金比例为 10%
A 转入余额可得 $2.50 额度
A 未来现金提现计价为 CNY 0.80
```

购买额度基线必须是支付结算事务实际增加给 B 的订单额度，不能从实付金额、当前价格或当前兑换比例反推。

只有 A 在该笔充值完成时处于有效代理状态，才生成充值佣金。

### 3.3 两种奖励相互独立

| 注册邀请奖励 | 代理充值佣金 | 结果 |
| --- | --- | --- |
| 关闭 | 关闭 | 仅建立邀请关系，不发奖励 |
| 开启 | 关闭 | 注册时发放固定邀请奖励 |
| 关闭 | 开启 | 注册不发奖励，真实充值时发放代理佣金 |
| 开启 | 开启 | 注册奖励和真实充值佣金分别发放 |

两种奖励必须使用不同的账目和页面指标，不得混合成一笔“总奖励”。

## 4. 邀请关系

- V1 复用现有 `aff_code` 作为邀请代码。
- V1 复用现有 `inviter_id` 保存 B 的直接邀请人 A。
- 邀请关系在注册完成后不可由普通用户修改。
- A 不需要开启代理，也可以分享邀请链接并获得已启用的注册邀请奖励。
- B 注册时 A 必须是有效、可用的用户，禁止自邀。
- 邀请人数按成功建立邀请关系的用户数统计，与注册奖励金额是否为零无关。
- A 后续开启代理后，B 在此后发生的新充值可以产生佣金；开启代理前的历史充值不追溯补发。

## 5. 代理资格

### 5.1 全局配置

管理员可以配置：

- 是否开启代理充值佣金。
- 开启代理所需的已核验充值总额。
- 资格币种直接使用 Epay 结算币种，不提供第二个可编辑币种配置，也不跨币种累计。
- 全局充值佣金比例。
- 佣金等待期，默认 7 天，允许配置为 0 天。

门槛金额使用最小货币单位存储。例如 `$100.00` 保存为 `10000` 美分。

### 5.2 用户级权限

用户管理界面提供三态配置：

- `inherit`：遵循系统充值门槛，默认值。
- `allow`：管理员允许用户跳过充值门槛。
- `deny`：禁止用户开启或继续使用代理充值佣金。

资格计算：

```text
代理充值佣金全局开启
且用户权限不是 deny
且以下条件之一成立：
  - 用户权限为 allow
  - 用户权限为 inherit，且已核验充值总额达到门槛
```

### 5.3 代理状态

- `inactive`：当前尚未开启代理，或撤销 `allow` 后未达到系统门槛、需要重新开启。
- `active`：代理正常，可从后续真实充值获得佣金。
- `suspended`：代理佣金权限被管理员暂停。

达到门槛只代表可以开启，用户仍需主动点击“开启代理”。管理员设置 `allow` 也不自动激活。

调整全局门槛只影响尚未开启的用户，不自动取消已经开启的代理。管理员将用户权限设置为 `deny` 时，已开启代理变为 `suspended`。

管理员将用户权限从 `allow` 或 `deny` 恢复为 `inherit` 时，立即按当时的系统充值门槛重新判断。达到门槛的已开启用户恢复或保持 `active`；未达到门槛的用户回到 `inactive`，需要满足门槛后重新开启。该动作不删除历史邀请、注册奖励、佣金流水或已经转入的额度。重复保存 `inherit` 以及仅修改全局门槛，都不会批量重算或取消已有代理。

暂停只影响充值佣金。该用户的邀请链接、邀请人数、历史注册邀请奖励仍然保留；如果注册邀请奖励全局开启，仍按独立规则处理注册邀请奖励。

## 6. 已核验充值口径

V1 仅将满足以下全部条件的 Epay 充值计入资格和佣金：

- 支付回调签名验证成功。
- 回调状态明确为支付成功。
- 内部订单存在且支付渠道为 Epay。
- 回调实付金额可解析且大于零。
- 回调实付金额与内部订单应付金额完全一致。
- Epay 平台交易号存在。
- 订单由支付回调完成，不是管理员人工补单。

Epay V1 回调不携带可核验币种，因此 `paid_currency` 使用下单事务从主库读取的商户结算币种快照。“已核验”表示支付状态、实付金额和平台流水已由签名回调确认，不表示渠道另外签名确认了币种字段。

明确排除：

- 注册赠送额度。
- 注册邀请奖励和代理佣金转入。
- 兑换码、套餐额度和管理员额度调整。
- 管理员人工完成的充值订单。
- 金额异常、缺少平台流水号或缺少支付凭据的订单。
- V1 范围外的支付渠道。

历史订单如果缺少实付金额、币种或平台交易号，不自动计入。后续如需补录，必须通过独立的管理员核验和审计流程完成。

V1 的管理员“佣金冲正”只作废 A 的佣金，不代表 Epay 已退款，不扣回 B 的充值额度，也不从已核验充值总额中删除原支付。渠道真实退款必须在后续版本以独立外部退款凭据和原子额度调整实现。

## 7. 佣金计算

### 7.1 比例

佣金比例使用基点存储：

```text
1% = 100 bps
50% = 5000 bps
100% = 10000 bps
```

比例范围为 `0` 至 `10000`。每笔佣金保存支付完成时的比例快照；管理员修改比例只影响之后完成的充值。

### 7.2 双口径计算基数

同一笔佣金同时保存两种不可变计价结果：

- 转入余额奖励：基于该充值订单实际记入 B 主余额的购买额度快照 `purchased_quota`。
- 未来现金提现：基于 Epay 签名回调核验通过的真实支付金额 `paid_amount_minor`。

`purchased_quota` 必须直接取自支付结算事务实际增加给 B 的 `TopUp.QuotaAmount`，不得根据实付金额、当前单价、当前 `QuotaPerUnit`、用户组倍率或折扣重新推算。这样佣金使用的购买额度和 B 实际到账额度来自同一个订单事实。

```text
cash_commission_minor = floor(paid_amount_minor x rate_bps / 10000)
gross_reward_quota = floor(purchased_quota x rate_bps / 10000)
reward_quota = gross_reward_quota - debt_offset_quota
```

购买额度不包含注册奖励、兑换码、管理员赠送或与该充值订单分离的促销赠送。所有计算使用整数最小单位和项目统一的安全额度转换函数，禁止裸 `float64 -> int` 转换，禁止产生负数额度。

### 7.3 示例

USD 结算：

```text
购买额度：$50.00
实付金额：$50.00
佣金比例：50%
未来现金提现计价：$25.00
转入余额奖励：$25.00 额度
```

非 USD 结算：

```text
购买额度：$25.00
实付金额：¥8.00
佣金比例：10%
未来现金提现计价：¥0.80
转入余额奖励：$2.50，即 `1,250,000 quota`（当 `QuotaPerUnit = 500,000`）
```

## 8. 佣金生成条件

每笔佣金必须同时满足：

- B 存在有效 `inviter_id`，对应邀请人 A。
- A 与 B 不是同一个用户。
- A 在支付完成时处于 `active`。
- 代理充值佣金全局开启。
- 充值满足“已核验充值口径”。
- 充值完成时间不早于 A 的代理开启时间。
- 同一个充值订单尚未生成佣金。

V1 对 B 的每一笔符合条件的真实充值生成佣金，不限首次充值。

必须以充值订单 ID 建立唯一约束，保证重复回调、并发回调和服务重试不会重复发放佣金。

## 9. 佣金生命周期

```text
支付成功 -> pending -> available -> transferred
                         \
                          -> reversed
```

- `pending`：等待期内，不可转入余额。
- `available`：等待期结束，可以转入主余额。
- `transferred`：已经转入主余额。
- `reversed`：管理员冲正后佣金作废。

等待期为 0 天时，可以在支付完成后直接进入 `available`。

### 9.1 转入余额

- 注册邀请奖励与充值佣金分别转入，不共用一条流水。
- 转入操作必须使用事务和行锁。
- 同一笔可用佣金最多转入一次。
- 转入成功后增加 A 的主额度，并记录转入流水。
- 支付合规未确认时，不允许转入。
- A 必须仍处于 `active` 且权限不是 `deny`；`suspended` 用户只能查看历史记录，不能继续转入佣金。
- 转入金额使用 `reward_quota`，其毛额严格按订单 `purchased_quota` 乘支付完成时的佣金比例计算。

### 9.2 未来现金提现

- V1 在佣金创建时保存 `commission_amount_minor`，其值按真实实付金额和同一佣金比例计算。
- 前端只展示支付宝现金提现“未来支持”和每笔现金计价结果，不提供可点击的提现入口。
- V1 不创建提现订单、不绑定支付宝账户、不冻结现金佣金，也不调用任何支付宝接口。
- 后续启用现金提现时，同一笔佣金只能在“转入余额”和“现金提现”之间选择一种结算方式，必须通过原子状态转换防止双重结算。

### 9.3 佣金冲正

- 未转入的佣金直接标记为 `reversed`。
- 已转入的佣金不得直接把用户主额度扣成负数。
- 已转入部分形成佣金欠额，后续新佣金优先抵扣。
- 管理员从具体佣金执行冲正，并由佣金记录关联原充值订单。
- 所有冲正必须保存操作者、原因、时间和关联充值订单。
- 佣金冲正不声明渠道退款成功，不扣 B 的充值额度，不改变原订单的已核验充值总额。
- 真实退款属于独立支付能力，不能复用佣金冲正接口伪造退款事实。

## 10. 数据设计

### 10.1 用户代理字段

建议在用户代理资料中保存：

```text
affiliate_access            inherit | allow | deny
affiliate_status            inactive | active | suspended
affiliate_activated_at      开启时间
affiliate_qualified_amount  开启时已核验充值金额快照
affiliate_currency          资格币种
```

不能用 `aff_code` 是否为空判断代理是否开启，因为现有用户可能已经拥有邀请码。

### 10.2 佣金流水

每笔佣金至少保存：

```text
id
agent_user_id
referred_user_id
topup_id                    唯一
provider_trade_no
paid_amount_minor
paid_currency
purchased_quota
unit_price_snapshot
commission_rate_bps
commission_amount_minor       未来现金提现计价
gross_reward_quota            转入余额毛奖励
debt_offset_quota
reward_quota
status
available_at
transferred_at
reversed_at
reverse_reason
created_at
```

佣金流水是审计事实，不允许覆盖历史金额、比例和价格快照。

### 10.3 邀请关系与注册奖励流水

现有 `users.inviter_id` 可以继续作为快速查询字段，但不足以独立证明邀请绑定和固定奖励是否已经执行。V1 应增加不可变的邀请关系与注册奖励记录：

```text
affiliate_referrals
  id
  inviter_user_id
  referred_user_id            唯一
  aff_code_snapshot
  bound_at

affiliate_signup_rewards
  id
  referral_id
  beneficiary_user_id
  beneficiary_role            inviter | invitee
  reward_quota
  status                      granted | reversed
  config_version
  created_at
```

- `referred_user_id` 唯一，保证同一新用户只绑定一个邀请人。
- `(referral_id, beneficiary_role)` 唯一，保证注册重试不会重复发放 A 或 B 的固定奖励。
- 邀请人数以邀请关系记录为准，不再依赖 `aff_count` 是否因奖励大于零而增加。
- 注册邀请奖励记录和充值佣金记录必须分表或通过明确的业务类型隔离，不能只依赖文本日志区分。

## 11. API 设计

### 11.1 用户接口

```http
GET  /api/user/affiliate/overview
POST /api/user/affiliate/activate
GET  /api/user/affiliate/commissions
POST /api/user/affiliate/invite-rewards/transfer
POST /api/user/affiliate/commissions/transfer
```

`overview` 返回：

- 邀请链接和邀请码。
- 邀请人数。
- 注册邀请奖励的可转金额和累计金额。
- 代理状态、权限来源和是否满足资格。
- 已核验充值总额、门槛及还差金额。
- 当前佣金比例和等待期。
- 待结算、可用、已转入及累计佣金。

所有金额使用最小货币单位并以字符串返回，避免 JavaScript 大整数和浮点精度问题。

### 11.2 管理员接口

```http
PUT  /api/user/:id/affiliate-access
GET  /api/admin/affiliate/commissions
POST /api/admin/affiliate/commissions/:id/reverse
```

管理员不能直接输入并覆盖用户累计佣金。异常处理必须关联具体佣金或充值订单。

## 12. 前端设计

### 12.1 侧边栏和路由

“个人”分组顺序：

```text
钱包
代理中心
个人设置
```

- 路由：`/affiliate`
- 图标：`Handshake`
- 入口不根据用户是否开启代理而隐藏。
- 入口仍受管理员侧边栏模块配置控制，建议配置键为 `personal.affiliate`。
- 注册邀请奖励和代理充值佣金均全局关闭时，可以隐藏入口。

### 12.2 钱包迁移

从钱包页移除现有邀请奖励卡，将以下能力完整迁入代理中心：

- 邀请链接。
- 复制邀请链接。
- 邀请人数。
- 可转注册邀请奖励。
- 累计注册邀请奖励。
- 注册邀请奖励转入余额。

钱包页继续负责充值、余额、订阅和资金记录，不再重复展示邀请信息。

### 12.3 代理中心结构

```text
代理中心
├── 邀请推广
├── 注册邀请奖励
├── 代理资格与状态
├── 充值佣金概览
└── 充值佣金明细
```

#### 邀请推广

对所有用户显示：

- 邀请链接和复制按钮。
- 邀请人数。
- 当前注册邀请规则。

未开启代理的用户仍可邀请并查看邀请人数及注册邀请奖励。

#### 注册邀请奖励

独立显示：

- 可转注册邀请奖励。
- 累计注册邀请奖励。
- 邀请人固定奖励规则。
- 被邀请人固定奖励规则。
- 转入余额按钮。

#### 代理资格与状态

未达标时显示：

```text
已核验充值总额
代理开启门槛
还差金额
充值进度
前往充值
```

达到门槛或管理员允许时显示“开启代理”。管理员禁止时显示不可开启状态，不影响基础邀请功能。

#### 充值佣金

只有已经开启代理的用户显示完整佣金数据：

- 当前佣金比例。
- 被邀请用户累计已核验充值。
- 待结算佣金。
- 可用佣金。
- 累计佣金。
- 佣金转入余额按钮。

未开启代理时显示功能说明和当前资格进度，不显示虚构佣金数据。

#### 佣金明细

桌面端使用表格，移动端使用纵向列表：

| 时间 | 被邀请用户 | 真实充值 | 比例 | 我的佣金 | 状态 |
| --- | --- | ---: | ---: | ---: | --- |
| 08-09 14:30 | us***23 | $50.00 | 50% | $25.00 | 待结算 |

被邀请用户信息必须脱敏，不展示完整邮箱、手机号或用户名。

### 12.4 用户管理

## 13. 安全与一致性要求

- 前端展示的充值总额不得作为激活或佣金依据。
- `activate` 必须在后端重新计算资格并保证幂等。
- 支付完成、用户充值额度、佣金流水创建应处于一致的事务边界。
- 订单锁必须使用项目跨数据库的 `lockForUpdate`。
- 佣金订单使用唯一约束保证幂等，不能只依赖进程内锁。
- 金额和比例使用整数或 Decimal 计算，不使用二进制浮点进行财务结算。
- 所有数据库逻辑必须兼容 SQLite、MySQL 和 PostgreSQL。
- 佣金创建失败不得静默吞掉，必须记录可关联充值订单的告警并支持安全重试。
- 普通用户不能查看其他用户的完整身份、充值订单或佣金明细。

### 13.1 当前实现

- 邀请关系、A/B 固定注册奖励、注册奖励转入、充值佣金、佣金转入、佣金冲正和佣金欠额均有主库业务事实。
- 资金事务同时写主库 outbox；`LOG_DB` 不在资金事务中同步调用，由系统任务异步投递。
- outbox 使用稳定事件键避免正常重试重复投递；即使日志投递失败，主库账本仍是最终事实来源。
- 支付回调日志只记录订单号、用户、错误分类等必要字段，不记录 Epay 密钥、签名原文或完整回调表单。
- 管理员资格覆盖和代理配置变更保存独立审计事实；配置采用单 JSON Option、版本 CAS 和完整校验。

### 13.2 V1 日志分层

V1 必须同时保留四层记录，不得只写一条中文文本：

1. **业务账本**：邀请关系、固定注册奖励、充值订单和佣金流水，是最终事实来源。
2. **用户可见日志**：让 A、B 在自己的记录中看到邀请奖励、充值佣金和转入结果。
3. **管理员审计日志**：记录资格覆盖、暂停、恢复、配置变更和佣金冲正。
4. **服务运行日志**：记录回调验签失败、事务失败、唯一约束冲突和日志投递失败，用于告警排障。

业务账本必须先于文本日志存在。即使日志数据库暂时不可用，也不能丢失邀请或佣金事实；恢复后应能从主库业务账本补发用户日志和审计日志。

### 13.3 必须记录的业务事件

| 事件 | 记录归属 | 用户可见 | 必要字段 |
| --- | --- | --- | --- |
| `affiliate.referral_bound` | A、B 的邀请关系账本 | A 可见邀请人数变化，B 可见邀请来源可选 | `referral_id`、A、B、绑定时间、邀请码快照 |
| `affiliate.signup_reward_granted` | A 或 B | 是 | `referral_id`、受益角色、奖励额度、配置版本 |
| `affiliate.signup_reward_transferred` | A | 是 | 转移额度、转移前后可用奖励、事务 ID |
| `affiliate.activated` | A | 是 | 资格来源、门槛、已核验金额、开启时间 |
| `affiliate.access_changed` | 管理员审计 | 否 | 目标用户、修改前后权限、操作者、原因 |
| `affiliate.commission_created` | A 的佣金账本 | 是 | `topup_id`、脱敏 B、实付金额、币种、比例、奖励额度、状态 |

### 13.4 日志字段与隐私

- 业务事件使用稳定的英文 `action`，展示文案通过前端 i18n 渲染。
- 金额保存为最小货币单位字符串，比例保存为 bps，额度保存为整数。
- 用户日志中的 B 必须脱敏；完整用户 ID、平台流水号和回调调试字段仅管理员可见。
- 不记录 Epay 密钥、签名原文、完整回调参数、Cookie、访问令牌或完整邮箱/手机号。
- 所有事件包含稳定事件 ID、关联订单/佣金 ID、创建时间和请求 ID，便于串联排查。
- 管理员配置、资格覆盖和冲正必须使用 `recordManageAudit` 同类结构化审计能力，并记录修改前后值，但不得记录密钥。
- 如果 `LOG_DB` 与主数据库分离，不能假设跨库事务。推荐在主库写入事务性 outbox，再异步、幂等地投递用户日志和管理员审计日志。

### 14.1 风险等级

- `P1`：可能造成资格绕过、奖励漏发、配置误用、历史数据错误或越权操作。

### 14.3 支付回调收敛结果

`controller.EpayNotify` 已先校验签名、商户 ID、支付状态、支付方式、平台流水和精确最小单位金额，再调用 `model.CompleteEpayTopUp`。结算事务为：

```text
数据库锁定 pending 订单
-> 校验支付凭据与金额
-> 标记订单成功
-> 增加 B 的充值额度
-> 按条件创建唯一佣金流水
-> 提交事务
-> 更新/失效缓存
-> 最后向支付平台返回 success
```

事务失败返回 `fail`，允许支付平台安全重试；精确重放返回 `success` 但不重复到账。数据库以 `(payment_provider, provider_trade_no)` 和佣金 `topup_id` 唯一约束兜底。下单事务从主库读取 Epay 币种，并保存应付最小单位、币种、应发额度、单位价格、额度比率、用户组倍率和折扣快照；回调不重新读取价格配置。

### 14.4 注册邀请链路收敛结果

- 密码、微信和 OAuth 新用户均在 `InsertWithTx` 的用户创建事务内建立邀请关系和双方固定奖励事实。
- `affiliate_referrals.referred_user_id` 与 `(referral_id, beneficiary_role)` 唯一约束防止重复绑定和重复奖励。
- 邀请人数与奖励是否为零解耦；聚合更新使用条件更新，不再用旧用户快照 `Save` 整行覆盖。
- 邀请码扩展为 8 位，并在唯一冲突时有限重试；邀请人解析校验状态且禁止自邀。
- 注册后边栏初始化和普通注册日志统一走同一个非资金 finalizer，不再承担邀请奖励发放。

### 14.5 配置和管理员权限风险

- 佣金比例直接决定平台支出，必须限制在 `0` 至 `10000 bps`，不得接受 NaN、无穷或负数。
- 门槛、比例、等待期和开关使用单个 JSON Option，由专用接口进行完整校验、版本 CAS 和原子保存；通用 Option 接口拒绝直接修改或使用大小写、空格变体绕过。
- 开启非零注册奖励或充值佣金必须要求支付合规已经确认。
- “允许成为代理”可以绕过充值门槛，属于财务权限。建议仅 Root 用户可操作，即使入口放在用户管理页面。
- 佣金冲正必须是 Root 权限，不能复用普通用户额度调整接口。
- 配置变更只影响新充值，佣金流水必须保存配置版本、比例、实付金额和实际到账购买额度快照。

### 14.6 并发能力与验证边界

- 邀请关系、双方固定奖励、用户聚合和 outbox 在同一主库事务中提交，并由唯一约束与条件更新承担多实例幂等。
- Epay 结算锁定订单和用户，订单、B 额度、佣金及 outbox 同事务提交；代理设置、合规和币种用一次主库查询取得一致快照，不使用全局排他配置锁。
- 注册奖励转入、佣金转入和佣金冲正均锁定相关用户/资料/佣金并执行状态条件更新；佣金转入与冲正统一按资料再佣金的顺序加锁，竞争只允许一个合法顺序获胜。
- SQLite 测试只证明事务正确性，不代表高并发吞吐。跨库 CI 覆盖 MySQL 5.7/8.4 与 PostgreSQL 9.6/16 的同邀请人并发注册、重复回调和转入/冲正竞争。
- 本地没有可用的 MySQL/PostgreSQL 服务，因此当前只能确认 SQLite、编译与 CI 配置；四个真实数据库结果必须以 CI 为上线门槛。
- 未启用 Redis 时限流仍是单实例状态，多实例总流量会随实例数放大；数据库唯一约束是财务正确性的最终防线，限流不能代替幂等。

### 15.2 部署与数据风险

1. `provider_trade_no` 从旧二进制的非空字符串语义改为可空字段并建立复合唯一索引。旧版本仍写空字符串，不能与新结构滚动混跑；必须停旧写入后一次性升级。
2. 启动迁移会把旧空平台流水归一为 `NULL`，并在发现重复非空平台流水时失败，禁止自动选择或删除冲突记录。
3. 存量 pending Epay 订单缺少当时的额度比例、价格、折扣和币种事实，无法安全复算；迁移前置检查发现任意此类订单就拒绝启动，必须先在旧版本排空或逐单人工处理。
4. 历史成功订单只有在金额、币种和平台流水证据完整时才回填 `completion_source=webhook`；缺证据订单继续排除，历史用户可能少算但不会把赠送或补单误算成真实入账。
5. V1 汇总是“已核验累计支付”，不扣除渠道侧线下退款；真实净入账需要后续接入唯一外部退款凭据、B 额度回收/欠额和退款账本。
6. Epay 币种是唯一资格币种来源；下单和代理概览从主库读取而不依赖多实例本地同步缓存，佣金开启期间拒绝修改 Epay 结算币种，避免门槛和佣金静默换币。
7. `/topup/summary` 是可复用只读事实接口；`activate` 始终在主库事务内重新汇总，不信任前端值。管理员配置接口的门槛金额和所有用户端金额均以字符串传输，避免 JavaScript 大整数丢失精度。
8. MySQL 默认不区分 Option 主键大小写；通用 Option 接口与模型层都拒绝受保护财务键的大小写、空格和前缀变体，配置只能走专用事务路径。
9. 主库 outbox 与资金账本同事务，因此日志库故障不会改变资金事实；LOG_DB 是派生审计副本，极端的 worker 租约过期并发重投仍可能产生同 `request_id` 的重复日志，运营去重应以该稳定 ID 和主库业务流水为准。

### 15.3 当前验证状态

- SQLite 的严格金额、重复回调、事务回滚、注册并发正确性、转入/冲正竞争、权限和完整签名业务流均有自动测试。
- 前端执行 i18n 同步、TypeScript、聚焦组件测试、格式和生产构建检查。
- MySQL 5.7/8.4、PostgreSQL 9.6/16 的工作流和并发用例已配置；真实四库结果仍需 CI 运行，不以本地 SQLite 绿灯替代。
- 上线前必须备份数据库、停止旧版本写入、排空或核对在途支付、执行迁移、检查 blocked/duplicate 报告，再恢复流量。

## 16. 风险矩阵与控制措施

| 风险场景 | 可能后果 | 防护措施 | 必测回归 |
| --- | --- | --- | --- |
| 伪造或异常金额回调 | 少收款、多发额度和佣金 | 验签、金额精确匹配、平台流水唯一、失败关闭 | 0、负数、超精度、非数字、金额不一致 |
| 重复或并发回调 | B 重复到账、A 重复佣金 | 数据库锁、条件更新、唯一约束、幂等结算 | 同进程、跨连接、模拟多实例并发 |
| 数据库在结算中途失败 | 订单、额度、佣金三者不一致 | 单事务、提交后响应、可安全重试 | 每个写入点故障注入 |
| 管理员修改价格或比例 | 历史佣金被重新解释 | 订单和佣金快照、配置版本 | 下单后改价格、支付后改比例 |
| 币种切换 | 门槛误判、现金计价归入错误币种 | 订单币种快照、禁止跨币种直接累计 | CNY/USD 分组和配置切换 |
| 注册并发 | 邀请人数或固定奖励丢失 | 原子增量、邀请奖励唯一流水 | 同一邀请人并发注册 |
| 转入与冲正并发 | 重复转入或无法追偿 | 行锁、状态机条件更新、欠额账本 | transfer/reverse 竞争 |
| 已转入佣金被管理员冲正 | A 已消费且不能直接扣成负数 | 等待期、佣金欠额、后续新佣金优先抵扣 | pending/available/transferred 分别冲正 |
| 管理员误设 100% 佣金 | 利润被快速耗尽 | 范围校验、醒目预览、RootAuth、审计 | 边界值和配置回滚 |
| 多账号刷注册奖励 | 固定邀请奖励损失 | 风控、注册验证、频率限制、异常邀请审计 | 同设备/身份批量注册策略验证 |
| 普通管理员越权 | 绕过门槛、冲正或放大支出 | RootAuth 或专用权限、审计 | 角色权限矩阵 |
| 缓存与数据库不一致 | 页面余额错误或重复操作 | 事务后失效缓存、数据库为最终依据 | 转入后立即查询、缓存失败 |
| 日志数据库写入失败 | 资金成功但用户/管理员无记录 | 主库账本为准、事务性 outbox、幂等补发 | LOG_DB 不可用后恢复并补发 |

### 16.1 残余业务风险

以下风险不能只靠代码完全消除，运营上必须接受或补充策略：

- 支付成功后发生线下退款，但 Epay 没有可靠退款通知。
- A 与 B 是不同账号但由同一实际控制人操作，形成自买返佣。
- 50% 等高比例佣金超过真实毛利。
- 历史邀请关系在 A 开启代理后开始为未来充值产生佣金，可能增加原本未预期的支出。
- 等待期结束并转入主额度后，A 可能已经消费，佣金冲正只能通过未来佣金欠额追偿。
- V1 没有渠道真实退款凭据、B 充值额度回收或支付退款欠额；运营不得把佣金冲正当作完整退款。

上线时必须保留全局关闭代理充值佣金的紧急开关。关闭后停止生成新佣金，但不得删除历史流水或改变已经生成的佣金状态。

## 17. 上线前置条件

Epay 回调已按以下条件失败关闭：

```text
金额解析失败
金额小于等于零
平台交易号缺失
回调金额与订单金额不一致
=> 不完成订单、不增加额度、不计入充值总额、不生成佣金
```

上线仍必须满足：

- 全量后端、race、前端构建与四库 CI 均通过。
- 备份数据库，并核对 `(payment_provider, provider_trade_no)` 非空重复报告为零。
- 停止旧版本写入后一次性切换，禁止新旧二进制滚动混跑。
- 在旧版本上确认 pending Epay 订单为零；新版本前置检查不通过时不得绕过或直接恢复支付流量。
- 保留一键关闭代理佣金的配置开关和数据库回滚方案。

## 18. 历史数据策略

- 已发放的注册邀请奖励不追回。
- 已有邀请关系继续保留。
- A 开启代理后，已有被邀请用户之后的新充值可以产生佣金。
- 代理开启前的充值不追溯补发佣金。
- 缺少支付凭据的历史充值不计入代理资格。
- 证据完整的历史成功 Epay 订单只补完成来源，不补发历史佣金。
- 在途旧 Epay 订单不自动补齐快照；先在旧版本排空，无法排空的订单必须逐单人工核对。
- 已有邀请码不代表已经开启代理。

## 19. 验收标准

### 19.1 注册邀请奖励

- 开关关闭时，注册只建立关系，不发固定奖励。
- 开关开启时，A、B 按配置分别获得固定奖励。
- 奖励金额为零时，邀请人数仍然正确增加。
- 注册重试不能重复发放奖励。

### 19.2 代理资格

- 低于门槛的 `inherit` 用户无法开启。
- 正好达到门槛时可以开启。
- `allow` 用户可以跳过门槛。
- `deny` 用户无法开启，已开启用户变为暂停。
- 前端伪造充值总额无法绕过后端检查。

### 19.3 充值佣金

- 只有真实核验充值产生佣金。
- A 未开启或已暂停时不产生佣金。
- 同一充值重复回调只生成一笔佣金。
- 佣金使用支付时比例、已核验实付金额和实际到账购买额度快照。
- 修改全局比例不改变历史佣金。
- 管理员补单不产生佣金。
- 佣金冲正可以关联原充值和原佣金，并且不改变 B 额度或已核验充值总额。

### 19.4 前端

- 未开启代理的用户可以看到邀请链接、邀请人数和注册邀请奖励。
- 钱包页不再重复出现邀请推广卡。
- 注册邀请奖励与充值佣金视觉和文案明确分离。
- 长金额、长链接和移动端布局无溢出或遮挡。
- 加载、空数据、失败、禁止、暂停和待结算状态完整。
- 所有新增用户可见文本完成多语言同步。

### 19.5 日志与审计

- 邀请绑定、A/B 固定奖励、佣金生成、可用、转入和冲正均有可关联业务记录。
- 用户只能看到自己的奖励和脱敏后的关联用户信息。
- 管理员资格覆盖、配置变更和佣金冲正均有结构化审计日志。
- LOG_DB 暂时不可用时资金事务仍以主库账本为准，恢复后可以幂等补发日志。
- 重复请求或日志重投不会生成重复业务账目；派生日志使用稳定 `request_id` 便于检测和折叠极端租约竞争产生的重复副本。

1. 将 Epay 金额异常处理改为失败关闭，并完成回归测试。
2. 完成已核验充值证据字段和通用汇总接口。
3. 增加代理资格、状态和管理员配置。
4. 增加邀请关系账本、注册奖励账本、佣金账本和事务性日志 outbox。
5. 增加佣金幂等生成、等待期、转入和冲正。
6. 增加代理中心路由并迁移钱包邀请卡。
7. 增加用户管理代理权限和管理员配置界面。
8. 完成跨数据库、并发回调、日志补发、佣金冲正和前端响应式验证；四库真实运行以 CI 为准。
