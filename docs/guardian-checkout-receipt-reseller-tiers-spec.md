# Claude Guardian 下单来源、付款收据与代理等级设计

日期：2026-11-11。状态：v0.2 已按用户授权完成本地实现与验证，未部署。

实现基于本地 `52cc6aeab`；保留支付核心链路，不发送真实邮件、不部署。以下描述本地实现，不能据此推断生产环境状态。

## 1. 目标与范围

用户需求：

1. 下单前询问「你是从什么渠道认识我们的」，包含 Linux DO、GitHub、B站、QQ，其他。
2. 提供客户订单付款收据查看及邮件通知（要包含收据）。用户已明确是客户付款收据，不是代理提现收据。
3. 支持一级、二级、三级代理分类；每个等级统一维护供货价，新增代理无需逐项重填；支持批量调整并重做代理管理布局。

本稿建议：等级仅代表供货价格档位，不形成上下级关系或多层分佣；原有平台收款、交付、代理差价、手续费及退款规则继续使用。独立店铺域名仍按 `guardian-reseller-spec.md` 第 11 节单独推进。

## 3. 下单来源

### 3.1 交互

在结算弹窗联系方式之前增加单选项：

> 你是从什么渠道认识我们的？
>
> Linux DO / GitHub / B站 / QQ / 其他

- 新订单必选，初次不默认选中，避免虚假归因。「其他」为本稿建议，避免四个选项无法覆盖时被迫乱填；不追加自由文本。
- 再次下单可预填该用户最近一次有效选择，但允许修改；每张订单独立保存。
- 直营、代理、新购、续费使用同一字段，不因入口不同跳过。
- 未选择时显示字段错误并保留已填表单，不进入支付。
- 认识渠道和成交代理是两个维度：选择 GitHub 不覆盖代理归属，选择 QQ 也不代表某个特定代理。

### 3.2 数据与查看

- 建议字段 `discovery_channel`：`linuxdo / github / bilibili / qq / other`。新建订单入口校验枚举一次，内部传递确定值。
- 历史订单为空，显示「未记录」；不推测、不批量补成某个来源。
- 后台订单表新增可选列和筛选，详情固定展示；客户订单详情可展示原选择。
- 第一版不新增来源统计大屏、不跟踪跨站行为，也不采集 QQ 群号或账号。

## 4. 客户付款收据

### 4.1 生成与查看

- 服务器确认支付成功后生成，一张订单只有一份付款收据；支付回调重放或支付返回页再次确认不会重复生成。
- 待付款、已关闭且未实际付款的订单不展示「查看收据」。已付款后处于排队、交付等状态均可查看。
- 客户入口：「我的订单」卡片／详情 → 查看收据；管理员入口：统一订单详情 → 付款收据。
- 收据使用独立固定模板（A5 横向 210 × 148 mm），站内页面通过独立文档预览，手机按比例缩放；打印／另存 PDF 直接使用同一模板，不截图、不打印页面外壳、导航或操作按钮。第一版不新增服务端 PDF 生成依赖或邮件附件。
- 访问复用现有登录会话，服务端校验订单所有者或管理员。收据编号不能作为访问凭证；不提供匿名公开链接。

### 4.2 收据内容

| 区域 | 内容 |
| --- | --- |
| 抬头 | Claude Guardian 付款收据、稳定唯一收据编号、原订单号 |
| 付款信息 | 付款时间、币种 CNY、支付方式、原实付总额 |
| 商品明细 | 下单时商品名称、单次／月付／季付／年付、对应服务金额、所选 MAX 或 Ultra 首月加购金额 |
| 收款说明 | 平台收款及服务信息；展示名称沿用已配置业务信息，不虚构公司名称或税务信息 |
| 当前退款状态 | 未退款／退款处理中／已退款，以及有已确认记录时的实际退款金额和时间 |
| 操作 | 打印／另存为 PDF、发送至账户邮箱、返回订单 |

收据注明「本收据用于记录订单付款，不作为税务发票」。付款金额及商品快照固定；退款后保留原付款事实，追加展示当前退款结果，不把原实付改为零。无法从旧订单可靠确认的明细显示未记录，不能用当前商品价格补写。

客户收据不包含代理供货价、代理收益、内部交付备注、完整支付回调或凭据。代理不能代客户读取或发送收据。

### 4.3 历史订单

- 历史已付款订单允许首次查看时按可信订单快照创建收据，编号生成保持唯一。
- 付款时间沿用原时间，收据生成时间另记，不能伪装成历史已出具。
- 不自动向全部历史买家补发邮件；客户可主动发送自己的历史收据。
- 历史退款信息不全时明确显示「退款明细未记录」，不推导退款额。

## 5. 邮件通知

第一版邮件范围为「付款成功及收据」，不额外加入排队提醒、营销邮件、代理提现通知或到期提醒。

- 自动邮件：支付成功、收据生成后，向客户当前账户已绑定邮箱发送一封付款通知。
- 结算弹窗显示脱敏接收邮箱和说明；没有可用账户邮箱时显示「付款后可在我的订单查看收据；绑定邮箱后可发送邮件」，不阻止付款。
- 联系方式里的 Email 不自动作为收据地址，避免把联系资料与账户邮箱混为一谈。绑定邮箱沿用现有账户设置流程，本功能不改认证流程。
- 邮件包含商品、订单号、实付、付款时间和站内收据链接；不包含联系方式、管理员备注、代理成本、账号密钥。链接需要登录查看。
- 发送时记录接收地址快照；客户主动重发时使用当前绑定邮箱，界面先显示脱敏地址，不允许输入任意收件人。
- 邮件投递状态区分「待发送／已提交邮件服务器／发送失败／无可用邮箱」。SMTP 接受不能写成「客户已收到」。
- 客户收据页和管理员订单详情可查看发送状态并重发；重发沿用项目限流方式，建议同订单 60 秒内不重复提交。

### 5.1 最小可靠发送方案

支付成功后仅同步调用 SMTP，会出现付款已完成但 SMTP 临时故障导致邮件丢失、无法补发的问题；这是外部服务正常失败路径，不应让邮件失败回滚付款。

遵照用户要求，不改支付事务或回调：新建订单时标记需要收据通知，已有系统任务每 15 秒检查已付款订单，生成每订单唯一收据及待发送状态，然后异步发送。历史订单没有此标记，不自动群发。已知临时发送失败按 1／5／30 分钟有限重试，最多尝试 4 次；投递结果不确定时停止自动重试，页面显示结果未知，允许主动重发。SMTP 接收不等于用户已收到，不承诺严格只送达一次。

该设计只增加 Guardian 收据／投递记录和一个现有任务框架的处理器，不引入独立消息队列。上线前验证站点链接和 SMTP 配置；本轮本地验证不发送真实邮件。

## 6. 代理等级与批量供货价

### 6.1 定价模型

- 固定三个等级：一级、二级、三级。一级建议用于最优惠供货档；不根据销售额自动升降级，管理员决定等级。
- 每个「等级 × 商品」维护一套供货授权和价格：单次／月付、季付、年付、MAX 首月、Ultra 首月。不同商品和周期仍各有价格，“填一次”指每级每商品只配置一次，而非所有商品同价。
- 新增代理时选择等级，自动继承该等级已开放商品及供货价；代理仍设置自己的零售价和上架状态，不自动开售。
- 修改等级供货价后，该级继承代理的新订单报价立即使用新价；不需要逐代理复制或点击更新。
- 代理独立零售价不随供货价变化。供货上调导致现售价不能覆盖成本时，沿用现有停售规则，并明确提示「需调整售价」；不偷偷替代理涨零售价。
- 等级价格为空／0 的可选规格表示未开放，不能解释为免费。商品自身未开放的规格不能由等级配置强行开放。

### 6.2 个别报价与授权

为兼容现有业务，保留「跟随等级」与「独立配置」两种来源，以商品为单位切换；不增加五个价格字段分别继承的复杂规则。

- 跟随等级：该商品授权及所有供货规格由等级配置决定。
- 独立配置：沿用该代理该商品原有授权及全套供货价；支持单独禁售某代理的某商品。
- 恢复跟随等级须展示替换前后价格与授权差异，确认后清除该商品独立配置。
- 切换代理等级仅影响跟随等级的商品，独立配置保留并在预览中列出。
- 暂停代理仍按原规则禁止新销售；调等级不会自动恢复资格。

### 6.3 批量操作

1. **等级供货价表**：一次编辑多个商品／规格，保存前展示改价差异、受影响代理数和低于成本的零售价数量。
2. **批量设置等级**：勾选代理 → 选择一级／二级／三级 → 预览 → 确认；页面明确保留哪些独立配置。
3. **批量恢复跟随等级**：选中代理和商品范围后，单独预览将被替换的独立配置，不默认全选清除。

第一版批量调价使用表格直接填最终金额，不增加百分比涨跌、公式调价或 Excel 导入。批量保存同一事务成功或失败，避免前端逐个请求造成部分改完且不易追踪。只处理明确选中的代理／商品，不隐式扩大到全部搜索结果。

既有待付款订单、已付款订单、供货与收益快照保持原值；新订单和新续费报价使用当前有效价。未付款订单沿用原有效期和已有支付处理语义，不因调价重新结算。

### 6.4 旧代理迁移

- 旧代理初始显示「待分级」，现有授权、供货价、零售价及上架状态全部保持独立配置。
- 管理员批量分配等级后，可以先保留独立价，再按预览显式恢复跟随等级。
- 新代理必须选择一个已配置等级；未配置商品时明确显示无可售商品。
- 不根据旧价格自动猜测等级，不自动把全部代理设成三级并改变报价。

- 代理详情用独立弹窗展示身份、等级、当前有效价及「跟随／独立」来源，支持单商品特殊价；不再以“先在弹窗选代理”为主管理路径。
- 用户管理现有资格开通／暂停入口保留，开通时增加等级；代理管理展示状态并链接到已有资格操作入口，不重复建设用户管理。
- 提现审核保留已有审核、凭证和人工打款流程，不新增提现收据。
- 手机端代理表使用卡片列表，供货价按商品展开编辑；保存按钮可达，避免将所有价格字段挤进一张横向大表。
- 无代理、等级未配置、无匹配结果、加载失败分别有明确状态；失败保留编辑值。批量确认页明确展示影响范围，提交中禁止重复提交。

复用方案：代理列表使用项目 `DataTablePage`、工具栏、批量操作和移动卡片能力；价格矩阵复用现有表格及输入组件；弹窗用 `Dialog`，批量生效确认用 `ConfirmDialog`，编号复制用 `CopyButton`，加载／错误／空态复用现有组件。已检查 `data-table/README.md`、公开导出、`ConfirmDialog` 及 Guardian 的 `ResellerRecords`／`ResellerOffersPanel` 调用方式。现有单代理报价表缺少等级列与批量选择，因此新增领域页面组合这些组件，不另造通用表格或弹窗。

新界面使用英文源文本 i18n key，金额沿用 Guardian 的人民币分→元封装，日期语言先经 `toIntlLocale`；沿用当前主题和受保护署名。

## 8. 数据与接口实现边界

以下为建议契约，具体命名在实现时服从现有接口组织：

| 对象／能力 | 建议变更 |
| --- | --- |
| GuardianServiceOrder | 增加 `discovery_channel`，保留历史空值 |
| GuardianReceipt | 每订单唯一，保存编号、生成时间及付款／商品必要快照；退款状态关联已确认业务记录 |
| GuardianReceipt 投递字段 | 与收据同表保存接收地址、状态、尝试次数、下次尝试时间和申请时间；不另建投递流水实体 |
| GuardianReseller | 增加等级；历史空等级表示待分级 |
| 等级商品供货配置 | 等级与商品唯一，保存授权、五项供货价和更新时间 |
| GuardianResellerOffer | 保留独立价与零售价，明确供货来源；报价读取统一解析等级或独立配置 |
| 客户接口 | 读取本人订单收据、请求发送到当前账户邮箱 |
| 管理接口 | 读取订单收据／投递状态；等级价格批量预览与保存；代理筛选、批量分级及恢复继承 |

等级调整、独立价覆盖、批量生效写入既有 Guardian 操作审计，保存操作者、对象及变更前后值。供货变更不触及 API 钱包、充值返佣或其他计费体系。现有访问控制与会话限制继续适用。

预览后提交时重新读取相关配置；若报价已变，返回需重新预览，避免覆盖另一管理员的改价。复用已有事务／更新时间能力，不新增通用工作流引擎。

## 9. 实施顺序与验收

建议按下单来源、收据与邮件、等级定价与管理布局三个功能边界实施，不与独立域名店铺捆绑。

验收应保护真实行为：

- 来源：未选择不能新建订单，四个指定渠道及其他正确落库；历史订单显示未记录；选择不改变代理归属。
- 收据：真实成功支付产生唯一收据；回调重复不重复生成；未付款不可出具；商品改名／改价不改旧收据；本人／管理员可读，其他用户及代理不可读客户收据。
- 邮件：支付成功只生成一条自动通知；SMTP 失败不影响付款，有限重试可观察；无邮箱仍可查看；手动重发使用当前绑定邮箱；历史订单不自动群发。
- 价格：同级代理共享供货价，新代理无需逐商品重填；独立价不被批量等级调价覆盖；低于成本的规格禁止新购；历史和待付款订单金额不变；暂停状态不被分级恢复。
- 迁移：真实 SQLite、MySQL、PostgreSQL 新库及最新发布版本代表性旧库升级，重复启动迁移；验证历史订单、报价、唯一约束和收益记录保留，记录实际版本与命令。不能只用单库测试代替。
- 前端：受影响行为测试、typecheck、目标文件 lint、构建；浏览器验证桌面与手机的结算表单、收据打印、代理筛选／批量确认及价格编辑。验证证据单独记录，不能把本 spec 当成测试已通过。

## 10. 本轮采用的默认选择

客户付款收据范围已由用户确认，用户随后授权开始实现。本轮采用：

1. 渠道必选，四个指定选项之外加「其他」。
